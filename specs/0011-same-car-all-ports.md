## Запрос / мотивация
Разбор прогонов CMA-ES на PERUN (0010) 2026-11-26 показал, что оптимизатор ранжировал кандидатов
не по параметрам, а по машине.

`train_cma.py` оценивает кандидатов параллельно на портах `3001+i`. В образе
`/usr/local/torcs/share/games/torcs/drivers/scr_server/scr_server.xml` слот 0 (порт 3001) — машина
`car1-ow1`, а слоты 1–9 (порты 3002–3010) — `car1-trb1`, другая машина, примерно в 1.7 раза медленнее.
То есть 9 из 10 оценок шли не на той машине:

| Прогон | Кандидатов | Хорошие на 3001 | Хорошие на 3002–3010 |
|--------|-----------:|----------------:|---------------------:|
| run1   | 360        | 28 / 36         | 0 / 324              |
| run2   | 120        | 12 / 12         | 0 / 108              |

Контрольный прогон: «медианный» кандидат, перезапущенный один на 3001, дал на g-track-1 **47.7 с**
против **89.6 с** в прогоне (там он попал на порт с `car1-trb1`).

Причина — не код, а конфиг `scr_server` в образе. Но `train_cma.py` должен был это поймать сам:
TORCS детерминирован, одни и те же параметры на разных портах обязаны давать один и тот же фитнес.

## Что меняем

### Сторона кластера (делает Hlib, здесь описано)
- **`hpc/scr_server.xml`** (новый) — копия файла образа
  `/usr/local/torcs/share/games/torcs/drivers/scr_server/scr_server.xml`, во всех 10 слотах (0–9)
  `car1-ow1`. Только для обучения: симулятор и конфиг соревнования не меняются — мы просто ставим машину
  соревнования на каждый слот.
- **`hpc/train_cma.sbatch`** — этот файл подменяет файл образа при запуске:
  `apptainer exec ... --bind "$CODE_DIR/hpc/scr_server.xml:/usr/local/torcs/share/games/torcs/drivers/scr_server/scr_server.xml:ro"`.
- **`.gitattributes`** — `hpc/*.xml text eol=lf` (как для остальных файлов `hpc/`, чтобы после checkout
  на Windows и `scp` на кластер не было CRLF).
- **`params/search_space.json`** — расширены границы, в которые упёрся лучший результат run1 (таблица ниже).

### `train_cma.py` — проверка портов
- **Поколение 0 нового прогона:** base-параметры оцениваются **на всех портах воркеров сразу** (одна
  волна, по одной оценке на порт, порт задаётся явно — `Evaluator.evaluate_on`, без общей очереди портов).
  В лог — строка на порт (`port check: port 3005 ok fitness …`).
  - разброс `max − min` ≤ `--port-check-tol` (по умолчанию **1.0** единицы фитнеса) → проверка пройдена;
  - разброс больше → `ERROR: port check failed: … 3001=…, 3002=…, …` и **выход с кодом 3**, CMA не
    запускается, `checkpoint.pkl`/`generations.csv`/`candidates.jsonl` не пишутся (тот же `--outdir`
    можно сразу запустить заново);
  - часть портов упала (код ≠ 0, таймаут) → то же, код 3 (статусы по портам в сообщении);
  - упали все → как раньше: `base evaluation failed`, код 1;
  - остановка сигналом → код 0, как раньше.
- **Опорное значение gen 0** — результат первого порта (3001), как и раньше (`base_f`, `best_so_far`,
  `best.json`/`best_result.json`).
- **Формат выходов совместим:** в `generations.csv` по-прежнему одна строка `gen 0`; `evals` = число
  оценок gen 0 (10 вместо 1), `best/median/worst` — по портам, `best_so_far` = результат порта 3001.
  В `candidates.jsonl` — по строке на порт (`gen 0`, `idx` 0…N−1, `port`); поле `port` теперь есть и у
  gen 0 (у остальных поколений было и раньше).
- **`port_check.json`** (новый файл в `--outdir`) — вердикт, допуск, разброс, по каждому порту: статус,
  фитнес, время, сводка трасс. Пишется и при провале.
- **`--skip-port-check`** — старое поведение (одна оценка base). При `--workers 1` проверка не нужна и не
  делается.
- **`--resume`:** по умолчанию проверка не делается. С **`--port-check-on-resume`** — та же проверка с
  base-параметрами прогона (из контрольной точки) перед продолжением; в CSV/JSONL ничего не пишется, только
  `port_check.json`; провал → код 3; если результат на порту 3001 отличается от `base_f` прогона больше
  допуска — `WARNING` (старые и новые поколения несравнимы). `train_cma.sbatch` этот флаг сам не добавляет.
- `--port-check-tol` < 0 → ошибка аргументов (код 2).
- Время: проверка идёт одной волной параллельно — gen 0 длится столько же, сколько одна оценка
  (≈ 17 с на 8 трассах).

### Параметры (границы поиска, `params/search_space.json`)
Значения драйвера по умолчанию (`params/default.json`, `DEFAULT_PARAMS`) не меняются — только границы.

| Параметр | Было | Стало | Почему |
|----------|------|-------|--------|
| `curv_speed_gain` | [0, 2] | [0, 5] | лучший run1 = 1.997 — у верхней границы |
| `steer_ray_gain` | [0, 1] | [0, 3] | лучший run1 = 0.941 — у верхней границы |
| `accel_gain` | [0.03, 0.5] | [0.01, 0.5] | лучший run1 = 0.0365 — у нижней границы |
| `dist_margin` | [0, 40] | [0, 40] (без изменений) | лучший run1 = 0.99 у нижней границы, но отрицательный запас бессмыслен |

Следствие: контрольные точки run1/run2 с новым пространством не продолжить (`--resume` проверяет
совпадение пространства) — run3 только новым `--outdir`.

## Что это значит для run1 / run2
- Лучшие наборы (run1 **792.4**, run2 **745.9**) были оценены на порту 3001 = `car1-ow1` — **они
  корректны** (фитнес — на машине соревнования) и годятся как стартовая точка / сравнение.
- Сама траектория поиска испорчена: 90 % оценок на `car1-trb1` давали заведомо плохой фитнес независимо
  от параметров, CMA-ES фактически учился «попасть на порт 3001». Медианы/худшие поколений и сходимость
  `sigma` run1/run2 интерпретировать нельзя.

## Как проверить
Локально (сделано, см. «Результат»): заглушка pycma (тот же API `ask/tell/stop/sigma`, через `PYTHONPATH`,
как в 0010) и тестовый оценщик с аргументами `fitness.py`, у которого через `--fitness-args` можно сдвинуть
фитнес на одном порту (`--bad-port P --bad-delta D`) или уронить один порт (`--fail-port P`):
```
python -m py_compile train_cma.py
python train_cma.py --help
python train_cma.py --outdir <tmp>/ok  --fitness-script <dummy> --popsize 10 --workers 10 --max-gens 2 --seed 7
python train_cma.py --outdir <tmp>/bad --fitness-script <dummy> --fitness-args "--bad-port 3005" --popsize 10 --workers 10 --max-gens 2
```

На PERUN (Hlib):
1. Скопировать код с `hpc/scr_server.xml` на кластер; убедиться, что в копии 10 раз `car1-ow1`:
   `grep -c car1-ow1 hpc/scr_server.xml` → 10.
2. Короткий прогон: `OUTDIR=/mnt/scratch/$USER/cma_runs/portcheck sbatch --exclusive -t 00:20:00 hpc/train_cma.sbatch --max-gens 1`
   → в логе 10 строк `port check: port 30xx ok fitness …` с одинаковым фитнесом, `port check passed`,
   gen 0 ≈ 976.6 (default на 8 трассах, как в 0009/0010), gen 1 без сбоев.
3. Отрицательная проверка (по желанию): тот же запуск без строки `--bind …scr_server.xml…` в sbatch
   (исходный конфиг образа) → `ERROR: port check failed …` с 3001 заметно лучше 3002–3010 и код выхода 3
   (`sacct -j <id> -o ExitCode`).
4. run3: `OUTDIR=/mnt/scratch/$USER/cma_runs/run3 sbatch hpc/train_cma.sbatch` (новый каталог, новое пространство).
   Успех: в `candidates.jsonl` хорошие результаты на всех портах примерно поровну; `best_so_far` ниже 745.9.

## Результат
Локальная проверка (2026-11-26, Windows, Python 3.11, numpy 2.4.6, заглушка pycma, тестовый оценщик):
- `py_compile` — OK; `--help` — новые `--port-check-tol`, `--skip-port-check`, `--port-check-on-resume`;
  `--dry-run` — OK.
- 10 портов, одинаковый фитнес → `port check passed: 10 ports, spread 0.000 <= tol 1`, gen 0
  `evals 10 base 987.118 (port 3001)`, дальше поколения 1–2; `generations.csv` — строка `0,10,987.118…`,
  `candidates.jsonl` — 10 строк gen 0 с `port`.
- Порт 3005 +40 → `ERROR: port check failed: … (spread 40.000 > tol 1): 3001=987.118, …, 3005=1027.118, …`,
  **код 3**; в `--outdir` только `run_config.json`, `base.json`, `port_check.json`, `work/`; повторный запуск
  в тот же каталог с одинаковыми портами — проходит.
- Порт 3010 +0.5 (в допуске) → проходит.
- Порт 3003 падает (`exit 3`), 4 воркера → `evaluation failed on some ports … 3003=exit 3`, код 3.
- Один воркер, оценка падает → `base evaluation failed`, код 1 (как раньше).
- `--skip-port-check` при «плохом» порте → одна оценка, `evals 1`, CMA идёт (старое поведение).
- `--resume` без флага — проверки нет; `--resume --port-check-on-resume` с «плохим» портом → код 3,
  с одинаковыми — `port check passed`, продолжение с gen 4, CSV без разрывов.
- `--port-check-tol -1` → ошибка аргументов, код 2.

Проверка на PERUN (2026-11-26):
- Ручная проверка: лучший набор run2 на всех 10 портах одновременно (g-track-1 + ruudskogen).
  Без подмены `scr_server.xml`: 3001 → 109.978, 3002–3010 → 228.140 (ошибка воспроизведена).
  С подменой: все 10 портов → **109.978**.
- По дороге: первая версия `hpc/scr_server.xml` содержала в XML-комментарии двойной дефис —
  TORCS отклонил файл (`parseXml: not well-formed at line 17`, `No driver for that race`), все оценки
  упали. Исправлено, в файле оставлено предупреждение. Файл пришёл на кластер с CRLF — добавлено
  `hpc/*.xml text eol=lf` в `.gitattributes`.
- run3 (задача 177102, `--base` = лучший набор run2, `--sigma0 0.15`, popsize 20, 8 трасс; sbatch теперь
  при продолжении передаёт `--port-check-on-resume`): `port check passed: 10 ports, spread 0.000` —
  все 10 портов 745.868. За 5 поколений: медиана ≈ 780 (в run1/run2 стояла ≈ 1440), лучший **704.98**,
  поколение ≈ 38 с, сбоев 0.

## Заметки / открытые вопросы
- Допуск 1.0 — с запасом: при детерминированном TORCS одинаковые запуски дают одинаковое время круга.
  Если на кластере окажется шум в сотых — допуск не мешает; если проверка будет падать на одинаковой
  машине — сначала разбираться, откуда недетерминизм, а не поднимать допуск.
- run3 стартовал от лучшего набора run2 (745.87): он оценён на порту 3001 = `car1-ow1`, т.е. честный.
- На соревновании scr_server-конфиг организаторов; машину соревнования (`car1-ow1`) стоит перепроверить
  по регламенту.
